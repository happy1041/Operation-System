#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
>How do you avoid overflowing the stack page?

In `setup_stack()`, we first tokenize the command line using `strtok_r()`, storing each token pointer in a local `argv[64]` array. We then push the argument strings onto the user stack **in reverse order** (from `argv[argc-1]` down to `argv[0]`), recording the resulting stack address of each string in `arg_addr[]`. After word-aligning `esp`, we push a null sentinel, then push the saved addresses from `arg_addr[]` again in **reverse order** (i.e., `arg_addr[argc-1]` … `arg_addr[0]`), so that `argv[0]` ends up at the lowest address — matching the C calling convention. Finally, we push `argv` (pointer to `arg_addr[0]`), `argc`, and a fake return address.

Stack overflow is partially mitigated by the 64-entry `argv[]` limit and the fact that all argument strings are copied into a `palloc`-allocated page (≤ 4 KB). However, we do **not** explicitly check that the total stack frame fits within PGSIZE; an extremely long command line could in principle cause a stack overflow.

#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` stores its state in a global (or thread-local) pointer, making it unsafe when two threads call it concurrently. `strtok_r()` requires the caller to provide its own `save_ptr`, so multiple threads can tokenize independent strings simultaneously without interfering — "r" stands for reentrant.

>A4: In Pintos, the kernel separates commands into a executable name and arguments.  In Unix-like systems, the shell does this separation.  Identify at least two advantages of the Unix approach.

1. **Flexibility / programmability**: The shell can implement wildcards (`*.c`), variable expansion (`$HOME`), quoting, pipes, and redirections before the kernel ever sees the command, without any kernel changes.
2. **Simplicity and security of the kernel**: The kernel only receives a pre-split `argv[]` array, keeping the argument-parsing logic out of privileged code and reducing the kernel's attack surface.

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

Each thread owns a `fd_table[128]` array of `struct file *` pointers. When a file is opened (`SYS_OPEN`), `filesys_open()` returns a new `struct file *`; it is stored at `fd_table[fd_next]` and `fd_next` is incremented. The integer index is the file descriptor returned to the user.

File descriptors are **unique within a single process** only. Two different processes can have the same integer fd (e.g., both use fd 3) pointing to entirely different files. There is no OS-wide fd namespace.

#### ALGORITHMS

>B3: Describe your code for reading and writing user data from the kernel.

All data access from user space goes through two validation helpers:

- **`check_ptr(ptr)`**: Rejects the pointer if it is NULL, above `PHYS_BASE` (not user virtual address), or not mapped in the current process's page directory (`pagedir_get_page` returns NULL). On failure it calls `syscall_exit(-1)`.
- **`check_str(s)`**: Walks the string byte-by-byte calling `check_ptr` on each address until it finds `'\0'`, ensuring the entire string resides in mapped user memory.

System call arguments are fetched with **`get_arg(f, n)`**, which computes `(int*)f->esp + n + 1`, calls `check_ptr` on both the first and last byte of the 4-byte word, then dereferences it.

For buffer arguments (read/write), we call `check_ptr(buf)` and, if `size > 0`, `check_ptr(buf + size - 1)`, verifying both endpoints. All `filesys_*` / `file_*` calls are wrapped in `lock_acquire(&filesys_lock)` / `lock_release(&filesys_lock)`.

>B4: Suppose a system call causes a full page (4,096 bytes) of data
>to be copied from user space into the kernel.  What is the least
>and the greatest possible number of inspections of the page table
>(e.g. calls to pagedir_get_page()) that might result?  What about
>for a system call that only copies 2 bytes of data?  Is there room
>for improvement in these numbers, and how much?

Our implementation only checks the **first and last byte** of the buffer (2 calls to `pagedir_get_page`), not every byte or every page boundary.

- **4,096-byte buffer**: least = 2 (both endpoints on the same mapped page), greatest = 2 (we never check more). The actual copy inside `file_read`/`file_write` does not call `pagedir_get_page` again.
- **2-byte buffer**: likewise 2 calls (start + end).

There is **room for improvement**: the optimal strategy would be 1 call when both endpoints lie on the same page, and ⌈size/PGSIZE⌉ + 1 calls at most when the buffer spans multiple pages. An alternative is to use the MMU-fault approach (install a page-fault handler that recovers gracefully), which amortizes the cost to zero explicit `pagedir_get_page` calls.

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

`SYS_WAIT` calls `process_wait(child_tid)`.

`process_wait` searches the caller's `children` list for a `child_info` with matching `tid`. If none is found, or if `ci->waited` is already true, it returns -1 immediately (prevents double-wait). Otherwise it sets `ci->waited = true` and blocks on `sema_down(&ci->sema)`.

When the child eventually calls `thread_exit()` → `process_exit()`, it writes its `exit_status` into `ci->exit_status`, sets `ci->exited = true`, and calls `sema_up(&ci->sema)` — waking the parent. The parent then reads the status, removes the `child_info` from its list, decrements `ref_count`, and frees the struct if the count reaches zero.

If the child exited **before** the parent called `wait`, the semaphore count is already 1, so `sema_down` returns immediately and the parent obtains the stored exit status without blocking.

>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

**Strategy: centralize validation in small helpers, terminate early.**

Rather than sprinkling `if (bad) { cleanup; return -1; }` throughout every syscall case, all pointer validation is delegated to `check_ptr()` and `check_str()`. These helpers call `syscall_exit(-1)` directly on failure, which invokes `thread_exit()`. Because `thread_exit()` always calls `process_exit()`, all cleanup (closing fds, releasing the exec file, waking the parent) happens unconditionally in one place regardless of how the process dies. No syscall case needs its own cleanup path for bad pointers.

**Example — `SYS_WRITE`:**
1. `get_arg(f, 0/1/2)` validates `esp+4`, `esp+8`, `esp+12` (the three arguments). Any bad address → `syscall_exit(-1)`.
2. `check_ptr(buf)` and `check_ptr(buf + size - 1)` validate the buffer endpoints.
3. If both pass, `lock_acquire(&filesys_lock)` is called, `file_write` runs, `lock_release` follows.

If step 1 or 2 fails, we call `syscall_exit(-1)` before acquiring any lock, so **no lock is held** when the process is torn down. There is no scenario where the filesys lock can be leaked, because we never acquire it before all validations succeed.

The one acknowledged gap: if a multi-page buffer has an unmapped interior page (endpoints are valid but middle is not), our endpoint-only check will miss it. In that case the kernel page fault handler in `exception.c` catches the fault, sets `exit_status = -1`, and calls `thread_exit()` — again reaching the same `process_exit()` cleanup path.

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

`process_execute()` allocates a `child_info` with `load_sema` initialized to 0 and places a pointer to it in the last bytes of the `fn_copy` page before spawning the child thread.

After `thread_create()`, the parent immediately calls `sema_down(&ci->load_sema)`, blocking itself. The child retrieves `ci` from the same page, runs `load()`, writes the result into `ci->load_success`, and calls `sema_up(&ci->load_sema)`. Only then does the parent wake up, check `ci->load_success`, and return `TID_ERROR` (mapped to -1 in `SYS_EXEC`) or the valid tid.

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

The `child_info` struct is heap-allocated and shared between P and C through `ref_count = 2`. Both parties decrement the count exactly once; the last one frees the struct. The semaphore `sema` (init 0) synchronizes the wait.

- **P waits before C exits**: P calls `sema_down` and blocks. C exits, writes status, calls `sema_up`. P wakes, reads status, decrements ref_count (→1 → not freed yet), removes from list. C had already decremented (→0 after P's decrement? No: C decremented first to 1, P decrements to 0 and frees). **No leak.**
- **P waits after C exits**: C has already called `sema_up`. P's `sema_down` returns immediately (count was 1). P reads the status, both decrements happen in sequence (C already did its to 1; P does to 0 and frees). **No leak.**
- **P exits without waiting, before C exits**: P's `process_exit` iterates its `children` list and decrements each child's `ref_count` (2→1). C still runs; when C exits, it decrements ref_count (1→0) and frees the struct itself. **No leak.**
- **P exits without waiting, after C exits**: C already set ref_count to 1. P's cleanup loop finds it, decrements (1→0), frees. **No leak.**

Special case: `waited = true` prevents a second `wait` on the same child from doing anything — it returns -1 without double-freeing.

#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

We chose the **verify-then-access** approach (calling `pagedir_get_page` before dereferencing) rather than the MMU-fault approach because:

1. It is simpler to reason about — pointer failures are caught at a well-defined point before any kernel state is modified.
2. It avoids the complexity of installing a recovery path inside the page-fault handler.
3. For Pintos Lab 2 the performance difference is negligible; the added latency of two `pagedir_get_page` calls per syscall is imperceptible.

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

**Advantages:**
- O(1) open, close, and lookup — array indexing.
- Simple implementation with no dynamic allocation per fd.
- Per-process isolation: one process's fd table has no effect on another's.

**Disadvantages:**
- Fixed maximum of 128 open files per process (indices 0–127, 0/1 reserved → max 126 user files).
- `fd_next` is monotonically increasing and never reuses freed slots within the same process lifetime, so a long-running process that repeatedly opens and closes files will eventually exhaust the table.
- 128 × 4 bytes = 512 bytes of `struct thread` space is always allocated, even for processes that open no files.

>B11: The default tid_t to pid_t mapping is the identity mapping.
>If you changed it, what advantages are there to your approach?

We did not change the mapping. In our implementation `tid_t` and `pid_t` are the same integer, which is the Pintos default. Since Pintos uses 1:1 thread-to-process mapping, there is no need for a separate pid namespace.
