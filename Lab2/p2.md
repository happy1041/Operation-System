>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?

首先使用 strtok_r() 解析命令行字符串，将每个参数的指针存储在局部的 argv[64] 数组中。然后，我们逆序将参数字符串压入用户栈，并将每个字符串压栈后的实际地址（对应的 esp）记录在 arg_addr[] 数组中。

#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

r 代表线程可重入，根据 C 标准库的定义，`strtok()` 利用全局静态 char 指针去保存字符串，不安全。这里 `strtok_r()` 通过从传入的 `save_ptr` 保存状态来避免全局静态变量，安全。

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

SYS_WAIT 在底层调用 process_wait(child_tid)，我们直接看 process_wait 的实现：   

process_wait 会遍历调用者的 children 列表，这个 children 列表里存储着由父子进程共享的 child_info 结构体。
尝试寻找 tid 匹配的 child_info 结构体。如果未找到，或者 ci->waited 已经被标记为 true（防止重复 wait），则立即返回 -1。否则，它将 ci->waited 设为 true，并调用 sema_down(&ci->sema) 阻塞当前进程。

当子进程最终调用 thread_exit() 进而触发 process_exit() 时，它会将自己的 exit_status 写入 ci->exit_status，将 ci->exited 设为 true，并调用 sema_up(&ci->sema)——唤醒沉睡的父进程。父进程醒来后读取状态码，将 child_info 从列表中移除，递减 ref_count，如果 count=0 则释放该结构体。

如果子进程在父进程调用 wait 之前就已经退出了，那么信号量的值已经变为 1，此时 sema_down 会立刻通过而不会阻塞，父进程可以直接读取到预存的退出状态。

指针的验证都委托给了 check_ptr() 和 check_str()。一旦验证失败，这些辅助函数会直接调用 syscall_exit(-1) 进而触发 thread_exit()。由于 thread_exit() 必定会调用 process_exit()，自然进行资源清理。

以 SYS_WRITE 为例：

- get_arg(f, 0/1/2) 会验证 esp+4、esp+8、esp+12（三个参数所在的位置）。遇到任何非法地址，立刻进入 syscall_exit(-1)。

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

process_execute() 在堆上分配一个 child_info 结构体并且在父子进程间，将其中的 load_sema 信号量初始化为 0，启动子线程。

在 thread_create() 返回后，父进程会立即调用 sema_down(&ci->load_sema) 将自己阻塞。此时子进程执行 load() 操作，将加载的布尔结果写入 ci->load_success，最后调用 sema_up(&ci->load_sema)。父进程才能被唤醒去 return。

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

我们通过在堆上分配共享的 child_info 结构体，并利用初始值为 2 的 ref_count（引用计数）机制来解决所有竞争条件。父子双方都持有指针，每退出一方就将计数减 1，最后一个离开的一方负责释放内存。同步则通过初始值为 0 的信号量 sema 来实现。

- P 在 C 退出前调用 wait：P 调用 sema_down 并被阻塞。C 退出时，写入状态码，调用 sema_up 唤醒 P。P 醒来读取状态，递减 ref_count（此时为 1，不释放内存），并将 ci 从列表中移除。由于 C 退出时已经递减过一次，最终 P 递减时发现计数归零，由 P 负责 free。

- P 在 C 退出后调用 wait：C 退出时已经调用了 sema_up，并将 ref_count 减至 1。P 随后调用 sema_down 时会立刻返回（不阻塞）。P 读取预存的状态码，递减 ref_count 至 0 并负责释放。

- P 未执行 wait 就提前退出，发生在 C 退出前：P 在执行 process_exit 时，会遍历自己的 children 列表，将所有子进程的 ref_count 从 2 减为 1。此时 C 仍在运行，且依然持有有效指针。当 C 最终退出时，它递减 ref_count（1 变为 0），由 C 自己负责释放结构体。

- P 未执行 wait 退出，发生在 C 退出后：C 退出时已将 ref_count 减至 1。P 退出时清理 children 列表，将其减至 0，由 P 负责释放。

特殊情况：waited = true 标志位确保了父进程无法对同一个子进程执行两次 wait 操作。第二次调用会直接返回 -1，从而避免了重复释放带来的内核崩溃问题。

#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

We chose the **verify-then-access** approach (calling `pagedir_get_page` before dereferencing) rather than the MMU-fault approach because:

1. It is simpler to reason about — pointer failures are caught at a well-defined point before any kernel state is modified.
2. It avoids the complexity of installing a recovery path inside the page-fault handler.
3. For Pintos Lab 2 the performance difference is negligible; the added latency of two `pagedir_get_page` calls per syscall is imperceptible.

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

**Advantages:**
- O(1) open, close, and lookup — array indexing.
- Simple implementation with no dynamic allocation per fd.
- Per-process isolation: one process's fd table has no effect on another's.

**Disadvantages:**
- Fixed maximum of 128 open files per process (indices 0–127, 0/1 reserved → max 126 user files).
- `fd_next` is monotonically increasing and never reuses freed slots within the same process lifetime, so a long-running process that repeatedly opens and closes files will eventually exhaust the table.
- 128 × 4 bytes = 512 bytes of `struct thread` space is always allocated, even for processes that open no files.

>B11: The default tid_t to pid_t mapping is the identity mapping.
>If you changed it, what advantages are there to your approach?

We did not change the mapping. In our implementation `tid_t` and `pid_t` are the same integer, which is the Pintos default. Since Pintos uses 1:1 thread-to-process mapping, there is no need for a separate pid namespace.
